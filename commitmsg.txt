Migrations, all additive, because SPEC-003 5.3 is a contract over fields SPEC-002 2's
schema has no column for: source.controller_id, .permission_evidence_url,
.permission_window_seconds, .row_version and UNIQUE (tenant_id, name);
removal_recipe.signing_key_ref, .max_attempts_per_window, .window_seconds, .enabled_at,
.disabled_reason and .row_version; UNIQUE (source_id, category) on
source_catalog_entry; and 0014 withdraws 0012's disabled_reason CHECK, which rejected
SPEC-003 5.3.10's own documented example with 23514. Every column is named by a
specification sentence; the two natural keys are choices SPEC-002 leaves open. Recorded
in ASSUMPTIONS.md 3.13 and EP-004 12, including the deviation from M6's "do not invent a
schema" instruction and why that instruction's stated condition does not hold.

Defects found and fixed while wiring:
  - registry and plugin declared DIFFERENT IdempotencyRequirement unions, so wiring
    requirementFor to the registry did not typecheck; a cast would have made the four
    public health routes demand an idempotency key.
  - the composition root passed requirementFor: () => undefined, so NO route ever claimed
    a key: every effect-bearing route ran with idempotency off while the registry said
    required. Same shape as the step-up defect fixed one milestone earlier.
  - DETAILS_ALLOWLIST had no key for the ETag SPEC-003 2.7 requires in a 412 body.
  - a 5.3 route raised SCHEMA_VALIDATION_FAILED where SPEC-003 5.3.7 names
    RECIPE_VERIFICATION_METHOD_REQUIRED.
  - a test read the current ETag with a token lacking vg.sources.read, so the ETag was
    undefined and a correct 412 looked like a concurrency bug; currentEtag() now asserts
    the read.

Not verified by this commit: no production recipe signing key exists (ADR-006 OPEN), so
POST /v1/sources/{sourceId}/recipes refuses 503 in any real deployment. Signature
verification is proven against a locally generated Ed25519 key pair and nothing more.
