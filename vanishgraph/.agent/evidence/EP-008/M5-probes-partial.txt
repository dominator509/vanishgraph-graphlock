TWO FINDINGS, BOTH RECORDED IN THE CODE THEY AFFECT
---------------------------------------------------

1. THE PER-PROBE TIMEOUTS SUM ABOVE THE TOTAL READINESS BUDGET. §7.2 declares timeouts of 300 + 200 + 200 + 400 + 300 +
   400 = 1800 ms AND a total readiness budget of 1500 ms, so a run in which several dependencies hang cannot satisfy
   both however the probes are scheduled. The runner therefore reports `budgetExceeded` and treats a breach as
   `NOT_READY` — reporting READY because every check eventually passed would hide an evaluation that took longer than
   the specification allows. A test asserts the 1800 ms sum so the finding cannot be forgotten if the timeouts change.
2. THE `reason_code` ENUM IS DECLARED, NOT ENFORCED AT RECORD TIME. The catalogue names each metric's own §6.5 row as
   the source of the bound for `reason_code`, and the registry cannot read a per-metric row: it enforces bounded sets for
   labels that carry one and records the source for the four whose bound lives elsewhere, so an out-of-enum reason code
   would NOT be refused by `record()`. The probe runner cannot produce one (its codes are a module constant the suite
   asserts equal to §6.5's eight), but the missing enforcement is a real gap and is recorded here and in the suite for
   whichever milestone closes it.
3. THE `dependency_key` BOUNDED SET NEEDED THE OVERALL-SERIES TOKEN. §6.5 says `vanishgraph_readiness_status` carries
   "one series per declared dependency plus an overall series", while the same row bounds `dependency_key` to the six
   declared names — the overall series could not be recorded inside its own declared bound. The catalogue now declares
   `overall` as a seventh value, the runner records the overall series under it, and the suite asserts the set is the six
   keys plus that token. This is a small specification gap, resolved in the direction the specification's own sentence
   describes rather than by inventing a second metric.
