MAJOR DEFECT FOUND AND FIXED, in my own 0002. The deferred constraint trigger
enforcing VG-DATA-005 read authority_grant under FORCE RLS using the SESSION's
app.tenant_id. A deferred trigger fires at COMMIT, when that setting reflects
only the LAST value the transaction set. A multi-tenant transaction therefore
validated tenant A's subject while pointed at tenant B, the grant row was
invisible, and a valid subject was rejected.

Observed directly: the two-tenant seed failed with "ProtectedSubject ...
requires a valid AuthorityGrant at commit" although the grant was inserted in
the same transaction. Isolated by experiment: tenant A alone seeded fine,
confirming the tenant switch was the cause. The function now scopes the lookup
to NEW.tenant_id and restores the previous setting. The two-tenant seed passes
with exactly one subject visible per tenant.

RECOVERY, done the honest way. Correcting an applied migration made the runner
refuse it (checksums are immutable, DOD-040) - correct behaviour, not an
obstacle to work around. Because these are disposable PRE-RELEASE databases
there is no history to preserve, so the container was torn down, re-provisioned,
and all four databases rebuilt from scratch. No released migration was rewritten.

Also confirmed: a deliberate one-line append to 0006 made verify report the
drift with both checksums and exit non-zero; restoring the file returned it to
clean.

Also recorded: check-rls-coverage.sh targets VG_TEST_DSN_OWNER (the _main
integration database), so it correctly reported "no tenant-scoped tables found"
until _main was migrated. That was the checker being right about an unmigrated
database, not a defect.
